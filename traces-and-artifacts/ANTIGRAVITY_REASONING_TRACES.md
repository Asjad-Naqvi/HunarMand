## 2. 💰 Price Estimation — Dynamic Pricing Engine

### Antigravity Reasoning (from `antigravity_traces_master_log.md`, Session 4)

> *"The pricing must be transparent and deterministic. Every component must be itemized for the consumer to see. I'll implement travel surcharge (distance-based), urgency multiplier (same-day), complexity tier (basic/intermediate/complex), surge detection (demand spikes), and loyalty discount (Haazir-subsidized, provider always gets full rate)."*

### Dynamic Pricing Formula (Antigravity Specification)

```
Pre-Discount Estimate = Base Rate + Travel + Urgency + Complexity + Surge

Final Estimate = Pre-Discount Estimate - Loyalty Discount
```

Component breakdown:
| Component | Formula | Example |
|-----------|---------|---------|
| **Travel Surcharge** | `max(0, distance_km - 3) × PKR 20` | 7km → 4km × 20 = PKR 80 |
| **Urgency** | Same-day: +15% of base rate | Base 1000 → +PKR 150 |
| **Complexity** | Basic +0%, Intermediate +10%, Complex +20% | Intermediate 1000 → +PKR 100 |
| **Surge** | ≥3 active requests in same sector+service (2hr window): +10% | → +PKR 100 |
| **Loyalty Discount** | Bronze 5%, Silver 10%, Gold 15% (platform-subsidized) | Silver 1000 → -PKR 100 |

### Tool Calls Generated by Antigravity
```python
# Antigravity-authored dynamic pricing block (from agent.py)
def calculate_price(base_rate, distance_km, urgency, complexity, surge_active, loyalty_tier):
    travel = max(0, distance_km - 3) * 20
    urgency_add = base_rate * 0.15 if urgency == 'same_day' else 0
    complexity_add = base_rate * {'basic': 0, 'intermediate': 0.10, 'complex': 0.20}[complexity]
    surge_add = base_rate * 0.10 if surge_active else 0
    pre_discount = base_rate + travel + urgency_add + complexity_add + surge_add
    loyalty_discount = pre_discount * {'none': 0, 'bronze': 0.05, 'silver': 0.10, 'gold': 0.15}[loyalty_tier]
    return pre_discount - loyalty_discount, {
        'base': base_rate, 'travel': travel, 'urgency': urgency_add,
        'complexity': complexity_add, 'surge': surge_add, 'discount': loyalty_discount
    }
```

### Complexity Classifier (Pre-Processing Step)
Antigravity added a keyword-based complexity auto-upgrader before pricing is computed:
```python

if any(kw in message for kw in ["bilkul kaam nahi", "completely stopped", "bar bar problem"]):
```

## 3. 📅 Scheduling Conflicts — Availability & Cancellation Handling

### Antigravity Reasoning (from `haazir_project_digest.md`, Section 4.2)

> *"Hard filter #3 is availability: provider must have an active schedule matching the requested time, must not be Unavailable/Suspended, and must not have a double-booking overlap within 30 minutes of travel buffer. This eliminates ghost-availability bugs."*

### Sequential Booking with Countdown
Antigravity designed the **Sequential Booking** model (no broadcast):
- Only the **single top-ranked provider** is notified at a time.
- Provider has a **15-minute countdown** to accept or decline.
- If the provider declines or times out → booking auto-expires, agent retries with next ranked provider.
- Database CRON jobs (Supabase Edge Functions) handle automatic expiry.

### Provider Availability Filters (Hard Filter)
```sql
-- Double-booking check (Antigravity-authored SQL logic in schema.sql)
-- No provider can have overlapping bookings within a 30-min travel buffer
SELECT * FROM bookings 
WHERE provider_id = $1 
  AND status NOT IN ('cancelled', 'expired', 'completed')
  AND scheduled_time BETWEEN ($requested_time - INTERVAL '30 minutes') 
                          AND ($requested_time + INTERVAL '30 minutes')
```

## 4. ✅ Confirmation Actions — Booking Flow & Self-Healing

### Antigravity Reasoning (from `antigravity_traces_master_log.md`, Session 5)

> *"The consumer_id passed from the frontend is 'anonymous' or a test string, not a valid UUID in the users table. Instead of failing, I should implement a self-healing pattern: validate the ID first, and if invalid, query the database for a real consumer record to use as fallback."*

### Self-Healing Consumer ID Resolution (Antigravity-authored)
```python
# Self-healing consumer_id resolution (agent.py)
valid_consumer = False
if consumer_id and "test_" not in str(consumer_id) and str(consumer_id) != "anonymous":
    chk = requests.get(f"{base_url}/users?id=eq.{consumer_id}", headers=headers)
    if chk.ok and chk.json():
        valid_consumer = True
        
if not valid_consumer:
    url = f"{base_url}/users?role=eq.consumer&limit=1"
    res = requests.get(url, headers=headers)
    if res.ok and res.json():
        consumer_id = res.json()[0]["id"]
        print(f"[Self-Healing] Dynamically resolved fallback consumer ID: {consumer_id}")
```

### Post-Pull Regression Fix (Phase 3, from `hunarmand_rebrand_walkthrough.md`)
After a `git pull` overrode the profile lookup logic, Antigravity re-implemented and hardened it:

> *"Re-implemented and hardened the profile lookup logic in AuthContext.tsx: (1) query public.users by Supabase Auth ID, (2) if not found, phone-number fallback, (3) if still not found, email fallback. If a matching row is found (e.g., +923111234509 matching consumer ID 9bf8cfbf…), it seamlessly uses the actual database-registered ID."*

```typescript
// AuthContext.tsx — hardened profile resolution (Antigravity-authored)
// Step 1: Match by Supabase Auth ID
let dbUser = await supabase.from('users').select('*').eq('id', authUser.id).single();
if (!dbUser.data) {
  // Step 2: Phone fallback
  dbUser = await supabase.from('users').select('*').eq('phone', authUser.phone).single();
}
if (!dbUser.data) {
  // Step 3: Email fallback  
  dbUser = await supabase.from('users').select('*').eq('email', authUser.email).single();
}
```

## 5. ⚖️ Dispute Escalation — Classification & Resolution

### Antigravity Reasoning (from `antigravity_traces_master_log.md`, Session 6)

> *"The dispute system requires: (1) classifying the dispute reason into one of 4 categories (DIS-01: pricing, DIS-02: quality, DIS-03: behaviour, DIS-04: delay), (2) updating the booking status to 'disputed', (3) inserting a row into the disputes table. The agent also needs to first call get_active_bookings so it knows which booking to dispute."*

### Dispute Tool Chain (Antigravity-designed 4-step sequence)
```python
# Antigravity-authored tool call chain in customer_instruction (system prompt)
# Step 1: get_active_bookings → find the relevant booking
# Step 2: classify dispute reason via keyword matching
# Step 3: PATCH bookings → status = "disputed"
# Step 4: POST disputes → insert dispute record

DISPUTE_CATEGORIES = {
    "DIS-01": ["price", "overcharge", "charged", "expensive", "too much"],
    "DIS-02": ["quality", "bad job", "poor work", "not fixed", "incomplete"],  
    "DIS-03": ["rude", "behaviour", "harassment", "unprofessional"],
    "DIS-04": ["late", "delay", "didn't show", "no show", "waiting"]
}

def classify_dispute(reason: str) -> str:
    reason_lower = reason.lower()
    for code, keywords in DISPUTE_CATEGORIES.items():
        if any(kw in reason_lower for kw in keywords):
            return code
    return "DIS-02"  # Default to quality dispute
```

### Tool Calls Generated
```
write_file: agent.py → file_dispute() function
  → Dispute classification via keyword matching on reason string
  → Two Supabase calls: PATCH bookings + POST disputes
  
write_file: agent.py → get_active_bookings() function
  → Prerequisite tool for cancel/dispute flows
  → Filters: status NOT IN (completed, cancelled, expired, disputed)
  
write_file: agent.py → customer_instruction (system prompt update)
  → Added explicit 4-step tool calling chain for dispute flow
```
